# Sources and adaptation notes

This skill is an original project-specific synthesis, not a claim that a public skill has been validated in this repository. Read these sources when changing the methodology; normal use does not require browsing them again.

- [Brendan Gregg: Performance Analysis Methodology](https://www.brendangregg.com/methodology.html): problem statement, workload characterization, hypothesis/prediction/test, time division, CPU versus off-CPU analysis, and suspending low-payoff tuning. Supplies the diagnostic framework and warnings against random changes.
- [Brendan Gregg: Active Benchmarking](https://www.brendangregg.com/activebenchmarking.html): observe the running workload to identify its real limiter and validate what the benchmark exercises. Statistical analysis cannot rescue a comparison of the wrong workload. Adapt long steady-state observation to the actual transient or intermittent gameplay event; hours of capture are not a requirement.
- [Brendan Gregg: USE Method](https://www.brendangregg.com/usemethod.html): utilization, saturation and errors guide resource questions. Apply relevant checks, retain unknowns, and connect them to the delayed action before assigning causality.
- [Unity: Best practices for profiling game performance](https://unity.com/how-to/best-practices-for-profiling-game-performance): frame-time budgets, profiling before/after, and separating CPU/render/GPU bottlenecks. Transfer the reasoning, not Unity-specific profiler commands, to PZ's JVM/Lua/native stack.
- [Google SRE: Service Level Objectives](https://sre.google/sre-book/service-level-objectives/): choose a few user-relevant indicators and explicit objectives; aggregate averages can obscure latency behavior. Transfer metric selection without importing a production-service SLO bureaucracy.
- [Google Benchmark: User Guide](https://google.github.io/benchmark/user_guide.html): warmup, repetitions, variation and interleaving to mitigate drift. Its microbenchmark settings do not define sufficient samples for rare game stalls.
- [pyperf: Analyze benchmark results](https://pyperf.readthedocs.io/en/latest/analyze.html): retain raw values/metadata and examine distributions and stability. Robust central summaries are not permission to discard the long frames that constitute the reported bug.
- [NVIDIA: CUDA C++ Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/): evaluate end-user requirements and the upper bound of improvement before investing in a hotspot. Apply the fraction-of-work argument to the relevant critical path, without assuming parallel stages add together.
- [ryanportfolio/Harness-Firmware: perf-loop](https://github.com/ryanportfolio/Harness-Firmware/blob/main/.claude/skills/perf-loop/SKILL.md): bounded rounds, one hypothesis per round, failed/inconclusive records, independent challenge, user-visible acceptance and evidence-based reopening. Its review structure is adapted proportionately, not a mandatory pair of reviewers for every small change.
- [irahardianto/awesome-agv: perf-optimization](https://github.com/irahardianto/awesome-agv/blob/main/.agents/skills/perf-optimization/SKILL.md): profiler-directed scope, impact/risk prioritization and preserving failed attempts for future sessions. Do not import universal 5%/20% thresholds, fixed diff-size limits, mandatory test/commit rituals, or blanket claims that runtime/assembly cost is untouchable.

The project adapts these methods through evidence-based continuation: each experiment must answer a useful question, and repeated work without diagnostic progress should stop. Earlier local numeric investigation quotas have been removed. Sample counts, timing windows and comparison design still follow the measurement question; they are not permission limits or universal statistical guarantees. Reuse prior results across chats instead of restarting discarded approaches.

Validation proportionality and the separation of code-quality retention from performance claims are project workflow decisions refined after a local pure-predicate cleanup triggered an expensive inconclusive gameplay comparison. They do not weaken the measurement standards above: use representative comparisons for substantive speed claims, retain uncertainty, and justify native checks by the actual behavioral risk.
