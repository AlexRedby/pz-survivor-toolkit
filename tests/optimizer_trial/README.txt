PZ Driving Optimizer Trial - consolidated v4 / B42.21 / 4a0e9546ec
Диагностика v3.3: WPR/ETW + JFR + CapFrameX по одной горячей клавише.

Расширенный профиль: xd3i-b42.21-d1bbdcf-bounded-v1
Основной режим: одиночная игра на одном ПК, один игровой процесс. Start-control.cmd и Start-optimized.cmd автоматически создают отдельный новый мир с готовой машиной; запуски выполняются по очереди. Host, второй клиент и второй компьютер для этого сравнения не нужны.
Используется тот же профиль оптимизаций, который поддерживает мультиплеер. SP здесь выбран для удобного измерения без дополнительной нагрузки локального сервера. Проверки Host/клиента сохраняются; успешный SP-замер сам по себе не подтверждает всю сетевую совместимость и не разрешает автоматический перенос в основной модпак.
Одна мировая сессия на запуск: перед повторным подключением, сменой сервера или другим миром полностью закройте игру и снова запустите CMD. Официальные preload helpers не умеют безопасно перезапускаться в той же JVM. Перезапуск требуется для воспроизводимого прогрева, не после каждого замера кадров.
Распакуйте в НОВУЮ папку. Режим по умолчанию изменён: поверх использованного мультиплеерного пакета эту сборку распаковывать нельзя. Старую папку с Profiles, Candidate и записями оставьте для сохранности результатов. Сборщик Collect-results.cmd и исправления Portable/порта/скачивания включены.

В пакете зафиксирован локальный объединённый кандидат: Toolkit 0.1.298, Java Patches 0.1.69 и полный выбранный набор из 67 Mod ID / 62 Workshop items. Это локальная сборка, она не объявляется опубликованным main. Её точная source_revision, общая с main база base_revision, список модов и версии находятся в pack-manifest.json и build-receipt.json; main_revision сохранён как совместимый алиас source_revision для лаунчера. При явно выбранных рабочих исходниках Java их fingerprint отмечен отдельно. Ревизия измеренного профиля xD3I указана отдельно в candidate-manifest.json и optimizer_candidate.profile_source_revision в build-receipt.json; она не обозначает ревизию этой сборки. Оба мода входят в архив. Python и Kotlin на Windows не нужны. Для автоматической записи JFR нужен распакованный Windows x64 JDK 25: можно использовать тот же, что для прежней записи. Лаунчер проверит инструменты до запуска игры, при необходимости попросит путь к папке с bin\jcmd.exe и запомнит его. Штатная Java игры не заменяется.

Workshop-моды поставляет Steam. Лаунчер проверяет наличие всего выбранного набора для B42.21, использует установленный Workshop в первую очередь и локальные копии выбранных сторонних модов как запасной источник. Если чего-то нет, запуск останавливается со списком недостающих Mod ID и Workshop-ссылками. Он не подписывается на моды и не обещает, что установленная версия Workshop уже обновлена: дождитесь окончания загрузок Steam.
Старый mods/default.txt и старые копии Toolkit из исходного профиля не определяют этот набор. Из исходного профиля берутся графика, клавиши и при необходимости сторонние локальные моды. Чужие или лишние моды в тестовый выбор не добавляются. После загрузки мира проверяется фактический список активных Mod ID.

Подробности неудачной попытки лежат в Candidate/last-download.json, незавершённый файл остаётся под уникальным именем .download и автоматически не используется.

Если Control уже записан, повторять его из-за ошибки загрузки не требуется.

Два проезда, одна горячая клавиша
1. Распакуйте новый архив в НОВУЮ папку, закройте игру и оставьте Steam запущенным. Дождитесь обновления Workshop. Откройте CapFrameX. Оставьте включённой запись датчиков Sensors, как в предыдущих замерах: CPU/GPU load, clock, temperature, power и память попадут в тот же JSON, если датчики доступны. Длительность и каталог захвата лаунчер задаёт сам; настройки CapFrameX на диске не переписывает.
2. Запустите Start-control.cmd: это весь закреплённый набор модов без оптимизатора. До запуска игры проверятся JDK 25 и API работающего CapFrameX. Если ZombieBuddy запросит разрешение, разрешите PZDrivingOptimizerBridge и обновлённый PZToolkitJavaPatches. После меню автоматически загрузится новый одиночный мир с исправной, заправленной машиной и ключом. Вручную создавать персонажа или подключаться к Host не нужно. Если игра перезапускается после разрешения Java-модов, запустите лаунчер повторно: это подготовка, запись ещё не началась.
3. Перед READY FOR CAPTURE Windows запросит UAC для отдельного помощника WPR: разрешите, чтобы записать события CPU/драйверов/диска/GPU. Игра и основной лаунчер не повышают права. Подготовка и сохранение WPR показывают прогресс. Если WPR отсутствует, права отклонены или профили недоступны, это явно отмечается; JFR и кадры всё равно можно сохранить. Дождитесь READY FOR CAPTURE. В игре установите 2560x1440, VSync off и одинаковое максимальное отдаление камеры в обоих проездах; лимит FPS оставьте одинаковым; сядьте в выбранную машину. Перед записью лаунчер покажет сохранённые значения разрешения/VSync/лимита FPS и конфигурацию датчиков. Лимит 60 допустим: он не объясняет падения ниже 60. Менять его ради записи не нужно; лаунчер сам настройки не меняет. Конфигурация датчиков на диске не гарантирует их фактическую запись: после проезда отдельно проверяются данные JSON. Находясь в окне игры, нажмите Ctrl+Shift+F8 ОДИН РАЗ. Не нажимайте отдельную клавишу записи CapFrameX и не запускайте Record-JFR.cmd.
4. Через несколько секунд прозвучит высокий сигнал: НАЧИНАЙТЕ ЕХАТЬ. Лаунчер уже запросил доступный WPR, подтвердил JFR и отправил команду 90-секундного захвата CapFrameX. Переключаться в другие окна и отсчитывать задержку не нужно. После двух низких сигналов кадры сохранены, можно остановить машину. Оставьте игру открытой до трёх высоких сигналов / DIAGNOSTICS DONE (JFR около 2 минут, затем WPR может ещё сохранять ETL; дождитесь финального статуса). Если звук недоступен, те же статусы выводятся в окне лаунчера. Затем выйдите из игры обычным способом и дождитесь завершения лаунчера.
5. Запустите Start-optimized.cmd. Первый запуск скачает официальный ZIP xD3I (~67 МБ), проверит SHA-256 и выберет только нужные неизменённые компоненты. Установщик автора не запускается. Загрузится другой свежий мир с той же стартовой точкой и моделью машины. Повторите шаги 3-4 с тем же маршрутом, графикой, масштабом и скоростью. Не оставляйте Control запущенным одновременно.
6. После закрытия обеих игр запустите Collect-results.cmd. Новые JSON и CSV уже привязаны к своим прогонам: вручную искать или перетаскивать их не нужно. Пришлите один ZIP из Diagnostics/PZDriving-Comparison-*.zip; скрипт напечатает полный путь. Если что-то не записалось, он сохранит доступные данные с отметкой Incomplete. Не переснимайте проезд до разбора результата.

Одна клавиша запускает согласованную последовательность, а не обещает старт с точностью до кадра: сначала доступный WPR, затем JFR и без ручного ожидания CapFrameX внутри его окна записи. frame-capture.json и JFR/capture.json содержат отдельные временные отметки запроса и подтверждения. Имена файлов не используются для угадывания пары. CSV проверяется по фактическому PID каждого кадра, JSON — по уникальной метке, процессу и длительности.

При INCOMPLETE или длинном низком сигнале сохраните данные и выйдите нормально. Скрипт не повторяет неизвестно завершившуюся команду запуска CapFrameX. Поскольку API CapFrameX выбирает процесс по имени, для автоматического захвата должен быть ровно один java.exe — запущенная тестовая игра. При другом Java-процессе скрипт сообщит об этом. Ctrl+Shift+F8 обрабатывается только когда тестовая игра на переднем плане. Конфликт уже занятой горячей клавиши также выводится явно.

Что собирается одновременно
- CapFrameX: времена кадров, FPS, включённые аппаратные датчики и raw CSV для проверки PID. JSON/CSV сохраняются автоматически в отдельной папке текущего запуска; проверенные файлы привязываются к нему по метке и SHA-256.
- JFR: CPU stack samples, сборки мусора и паузы JVM, выборка аллокаций, ожидания и события ввода-вывода, доступные в стандартном profile. Это профиль работы JVM, не дамп всей Java-памяти. Длительность 120 секунд; 90-секундный захват кадров начинается автоматически после подтверждения начала JFR и короткой технической задержки.
- Примерно раз в секунду: CPU и память именно игрового процесса. Примерно раз в две секунды: доступная системная память, накопленные I/O и page-fault счётчики процесса через лёгкие Win32 API. Во время проезда CIM/WMI не опрашивается. Частота ядер, температуры и GPU берутся из CapFrameX; события потоков и GPU дополнительно покрывает WPR. Page faults включают мягкие и жёсткие ошибки страниц и сами по себе не доказывают подкачку. Сохраняется стоимость опроса; медленный или недоступный необязательный источник отключается после первого такого ответа.
- Если установленный драйвер предоставляет nvidia-smi, не чаще одного раза в пять секунд: температура, частоты, загрузка, память, потребление и P-state GPU. Собственный Windows-сборщик не измеряет CPU-температуру; для неё используются включённые датчики CapFrameX, если доступны. Недоступные счётчики и поля отмечаются явно, а не заменяются нулями.
- WPR/ETW: приложенный ограниченный профиль PZTrial.light, события исполнения/переключения потоков, DPC/ISR, дискового I/O, hard faults и GPU. Без heap/allocation профиля. Каждому прогону соответствует отдельная именованная сессия. Помощник сохраняет только свою сессию, ограничивает длительность и объём временной записи; при неудачном сохранении останавливает только её. Запись в файл добавляет дисковую нагрузку в обоих режимах. Сведения о потерянных ETW-событиях сохраняются для анализа; нулевые потери не предполагаются.
- Раз в секунду в памяти сохраняются координаты, скорость и модель машины, масштаб камеры, пауза и число загруженных зомби. Во время езды наблюдатель не пишет эти строки в консоль: накопленные данные выводятся после выхода из мира/игры с исходными временными метками. Закрывайте игру штатно после завершения записи; при принудительном завершении процесса этот контекст может быть потерян и сборщик отметит его как неполный. Буфер хранит последние 1800 меток (около 30 минут); его переполнение также отмечается. Это число в загруженной игровой ячейке, а не только видимые зомби на экране. Наблюдатель ничего не спавнит и не меняет симуляцию.
- Модель CPU/GPU, драйвер, конфигурация модулей RAM, версия Windows, JVM и её параметры, настройки игры на момент запуска записи, точный набор модов, свежие stdout/stderr и console каждого запуска.

WPR v3.3 использует приложенный PZTrial.wprp вместо общего подробного профиля: события CPU/планировщика/диска и вывода кадров, стеки только для выборок CPU и ReadyThread. Убраны стеки переключений контекста, диска и графики. Профиль рассчитан на меньший объём; фактические накладные расходы на Windows ещё не измерены. SHA-256 профиля сохраняется в квитанции. Лимит временных файлов остаётся 2 ГиБ; при его срабатывании записывается увиденный размер. Ошибка сохранения ETL и результат проверки очистки записываются раздельно. Отсутствие профиля WPR само по себе не доказывает остановку всех ETW-сборщиков; неопределённость отмечается как Unknown. Без пригодного ETL сбор остаётся Incomplete. Для временных ETL после неудачного сохранения итоговый отчёт содержит ограниченный список путей и размеров. Эти непроверенные файлы остаются в исходной папке запуска и автоматически не попадают в ZIP; сохраните эту папку до разбора.

Проверка и исправление WPR без игры
Если прежний сбор завершился ошибкой 0x80010106, повторять поездку не нужно. Microsoft описывает эту ошибку старого WPR при сохранении и рекомендует Windows Performance Toolkit сборки 19650 или новее: https://devblogs.microsoft.com/performance-diagnostics/wpr-start-and-stop-commands/
Установите только компонент Windows Performance Toolkit из подходящего для вашей Windows пакета ADK, в стандартную папку. Официальная загрузка и совместимость версий: https://learn.microsoft.com/windows-hardware/get-started/adk-install . WinPE для этой проверки не нужен. Не копируйте отдельно wpr.exe: нужен установленный комплект Toolkit.
Запустите Test-WPR.cmd. Игра и CapFrameX для этого не нужны. Скрипт выберет установленный подписанный Microsoft ADK WPR, проверит версию и выполнит короткую 10-секундную запись с тем же профилем; после неё сохранение может занять больше времени. Системный WPR старее 19650 больше не используется. Запрашивается UAC только для помощника записи. Чужие сессии WPR не останавливаются.
Успех — Result: Passed, подтверждённый заголовок ETL, размер, SHA-256 и отсутствие собственных ETW-сборщиков. Это проверка записи, не тест FPS или накладных расходов. Пришлите WPR-check-result.zip из указанной скриптом папки WprChecks. В нём небольшой отчёт, версии, подписи и результаты команд; большой ETL остаётся рядом. При Failed также пришлите отчёт, сохранив всю папку; не начинайте новый игровой замер ради этой ошибки.
При обычной записи выбор и SHA-256 wpr.exe закреплены до повышения прав и перепроверяются помощником; путь и сведения о версии/подписи входят в receipt. Путь из PATH или отдельный скачанный executable не запускается. Исправление выбора версии и протокол проверены на macOS с моделированными Windows-ответами; реальное сохранение ETL новой версией на вашей Windows подтверждает именно Test-WPR.cmd.

Оба режима используют одинаковый сбор. JFR, WPR и опрос счётчиков добавляют нагрузку; она не считается автоматически вычтенной из результата. Collect-results сравнивает сохранённые настройки двух запусков, сообщает расхождения и прикладывает sensor-coverage.json с реально записанными датчиками. Это не проверка одинаковости маршрута или мира. Отдельные стресс-тесты, heap dump и видео сейчас не требуются. При аварии или сбое сохраните получившиеся данные и укажите обстоятельства: сбор не объявляет такой проезд успешным сравнением автоматически. ZIP содержит диагностические логи и локальные пути из них; сохранения и весь исходный профиль в него не копируются.

Цель двух проездов: проверить, стало ли меньше длинных кадров и изменился ли обычный FPS с этим набором оптимизаций. Свежие миры, случайные зомби и файловый кэш Windows не дают полностью одинаковых условий. Это ограниченное практическое сравнение; небольшую разницу нельзя автоматически приписывать оптимизатору. Если условия разошлись из-за аварии, отметьте это, не переснимайте многократно без разбора результата.

Каждый проезд — первый мир после полного запуска Java. Не выходите в меню для загрузки второго мира и не меняйте моды внутри этого запуска: upstream-прогрев однократный за JVM, после выхода AnimationSet очищается. Для новой попытки полностью закройте игру и снова запустите CMD.

Check-setup.cmd проверяет и готовит набор без запуска игры. Start-control.cmd запускает тот же полный набор в том же отдельном профиле без оптимизатора; исправление дашборда остаётся. Контрольный запуск не требует скачивания xD3I. Для сравнения нужны оба режима по шагам выше.

Portable CapFrameX поддерживается. Если Windows не возвращает путь процесса, лаунчер пробует QueryFullProcessImageName и затем локальный API на стандартном порту 1337. Если у Portable выбран другой порт и путь недоступен, укажите папку через -CapFrameXDir или порт через -CapFrameXPort. Запущенный процесс и ответ API по-прежнему проверяются; настройки программы не меняются.

Если WPR нужно явно исключить, добавьте -SkipWpr к обоим CMD. Это будет отмечено как неполный расширенный сбор. При следующем согласованном сборе используйте одинаковый режим WPR в сравниваемых запусках. ETL попадает в тот же итоговый ZIP автоматически. При Incomplete не переснимайте проезд до анализа.

Необязательная проверка мультиплеера
У хоста и подключающегося клиента должны быть одинаковые версии двух модов Toolkit из этого пакета и диагностический PZDrivingOptimizerBridge. Нужны все 67 Mod ID закреплённого набора и PZDrivingOptimizerBridge (итого 68). Диагностический ID PZDrivingOptimizerBridge необходимо включить в Mods хоста: игра при подключении заменяет клиентский список модов серверным. Один лишь локально включённый bridge не гарантирует сбор данных.
Для отдельной тестовой сессии хост запускает Start-control.cmd -Session Multiplayer -Menu и в Host выбирает готовый PZOptimizerHost. Клиент запускает Start-control.cmd -Session Multiplayer или Start-optimized.cmd -Session Multiplayer и выбирает Join. У хоста с -Menu не требуются CapFrameX, отдельный JDK для записи или WPR; сбор на подключающемся клиенте работает CMD с -Session Multiplayer. Профиль и мир отдельные; штатный набор модов и сохранения не переписываются. В мультиплеере стартовый мод PZDrivingBench выключен: пакет не создаёт машину, не телепортирует персонажа и не меняет погоду/зомби. Используйте обычную машину/маршрут.
Если используете другой Host-профиль, сначала подготовьте его отдельную тестовую копию с тем же набором и диагностическим ID; пакет не меняет действующий сервер автоматически. Хост может оставаться без оптимизатора, пока вы сравниваете Control/Optimized на подключающемся клиенте.

Для этого режима распакуйте отдельную копию пакета: использованный SP-профиль с другим набором не переписывается. Клиентский optimizer исключается из classpath дочернего сервера; сервер сохраняет штатные классы игры. Прогрев анимаций начинается после подключения и сброса клиентских кэшей. Автоматический захват CapFrameX требует ровно один java.exe: локальный Host с серверным Java-процессом для такого захвата не подходит. Эта необязательная схема требует отдельной машины Host и не входит в два основных проезда на одном ПК.
